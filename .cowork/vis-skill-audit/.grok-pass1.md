## 0. 탐색 로그 (ToT)

- 세운 가설:
  - **(1)** 스킬 문서만으로도 시드→실루엣→9패스→아이소 배치 파이프라인이 충분히 재현되어, 절차적 경로로 AAA 급 PC/Mob을 만들 수 있다.
  - **(2)** 실제 “멋지고 예쁜” 결과물은 `Artist`+`core/shading.dart`(계보 B) 핸드 아트에 있고, 스킬은 `HumanoidSpec`+`render/surface.dart`(계보 A) 위주라 **문서만 따르면 AAA에 도달하지 못한다**.
  - **(3)** 이중 트랙은 의도된 역할 분담(인게임 절차 vs 초상/갤러리 작품)인데, 스킬이 역할을 가르지 않아 AI가 잘못된 경로로 새 캐릭터를 만든다.
  - **(4)** 메타데이터·가상 API·카운트 오류가 산재해, 문서 신뢰도가 실행 단계에서 먼저 깨진다.

- 검증:
  - 가설 1 → `procgen.md`/`shading.md`/`isometric.md`/`spec.dart`/`humanoid_renderer.dart`/`main.dart`로 **절차 파이프라인 자체는 실재·동작** 확인. 다만 `humanoid_renderer`에 `paintContactShadow` 호출 0건, 눈은 gem blob 수준 → **AAA 달성 주장은 반증**.

## 1. 결론 요약

**이 스킬 문서만 읽은 AI는 “동작하는 2.5D 아이소 휴머노이드”는 만들 수 있어도, 현재 저장소의 PC/Mob이 보여주는 AAA 급 비주얼은 재현하지 못한다.**  
근거는 단순하다. **실제 예쁜 캐릭터는 전부 `Artist` + 계보 B(`core/shading.dart` + `anatomy.dart`의 `drawEye`/`rimBand`/`panelLine`/`castShadow`) 핸드 아트**인데, 스킬 본문은 **`HumanoidSpec` + 계보 A(`render/surface.dart` 9패스)** 를 정답 워크플로우로 가르친다.  
절차 파이프라인 문서(아이소 수식, Rng/branch, 원형 다이얼, Pose/IK) 품질은 높지만, **작품 경로의 핵심 레시피가 빠져 있고**, 문서·코드 불일치(이름 `abc`, 접촉 그림자 미사용, 가상 API)가 AI를 잘못된 API로 유도한다.  
수정보완은 코드를 건드리지 말고, **이중 트랙을 문서 최상단에 고정**하고 **계보 B 실전 레시피·참고 캐릭터 패턴·메타데이터 정합**을 넣는 방향이어야 한다.

## 3. 상세 분석

### 3.1 범위와 권위

| 영역 | 권위(실제 진실) | 스킬이 가르치는 것 |
|------|----------------|-------------------|
| 갤러리/대치 UI 비주얼 | `art/pc|mob/*` + `core/shading` + `anatomy` | 거의 없음 (architecture에 이름만) |
| 인게임 아이소 액터 | `HumanoidSpec` + `humanoid_renderer` + `render/*` + `rig/*` + `anim/*` | 스킬 본문의 전부 |
| 목표 품질 “AAA” | 현재 저장소 증거상 **핸드 아트 쪽** | 절차 체크리스트로 대체 |

분석 범위: **스킬이 AI를 올바른 경로로 이끄는가**. 코드 품질 자체 감사는 부차.

### 3.2 이중 파이프라인 (문서가 흐리는 핵심)

```
[트랙 A — 절차/인게임]                    [트랙 B — 작품/초상]
seed → HumanoidSpec → Body/Pose/solve     Artist.paint(t) 하드 포즈
     → Path(tube/blob) → paintSurface A        → Path + paintSurface B
     → IsoView squash, 8 facing                → kStage 고정, 단일 3/4 포즈
main.dart 뷰어                               entry.dart 로스터
```

- 트랙 A 문서화: **우수** (아이소 접지점만 투영, `wx+wy` depth, Rng.branch, 원형 대역 비겹침, 9패스 순서).
- 트랙 B 문서화: **architecture 디렉토리 한 줄 수준**. 그런데 **사용자 눈에 보이는 AAA는 전부 트랙 B**.

`anatomy.dart` 주석은 트랙 A의 존재 이유(“시드 휴머노이드”)와 정면으로 충돌한다. 스킬이 이 긴장을 설명하지 않으면, AI는 트랙 A로 “새 보스”를 만들어 **형제 같은 평균 실루엣**을 양산한다 — 바로 anatomy가 피하려던 실패.

### 3.3 AAA 아트 디렉션: 코드에 있고 스킬에 없는 것

실제 PC/Mob에서 반복되는, 문서에 거의 없는 기법:

1. **파츠 분할로 금속 밴딩** (`aldric` 주석: 흉갑·폴드론·뱀브레이스를 각기 다른 각도로 쪼갬).
2. **비율 왜곡이 곧 종** (`gorehide`: 머리 2/3, 어깨 5배; `vaelmorth`: 단일 spine).
3. **6겹 눈** (`drawEye`) vs 절차 렌더러 gem 눈 / 스킬 “4겹” 축약 (`silhouette.md:286`).
4. **후처리 윤곽·패널** — `rimBand`, `panelLine`, `castShadow`, `occlude`가 스티커 해제의 실전 도구. 스킬은 계보 A `paintContactShadow`+`occlusion`만 말함.
5. **캐릭터 전용 조명·이펙트** — 후광, 파리, 모트, infernal/spectral 프리셋. 스킬 규칙 7은 “씬 공유 LightRig”인데, 초상 트랙은 **의도적으로 캐릭터별 LightRig** (`creature.dart:43-44`, 각 PC의 `light` getter). 맥락(초상 vs 인게임) 분기가 문서에 없음.
6. **성격 한 줄 이펙트** — gorehide 파리, aldric 성스러운 모트. AAA 판독성의 큰 부분인데 체크리스트에 없음.

### 3.4 계보 A vs B: 섞으면 명암이 뒤집힘

| | 계보 A `render/` | 계보 B `core/shading.dart` |
|--|------------------|---------------------------|
| 방향 필드 | `keyDir` = 진행 방향 | `dir` = 광원을 보는 방향 |
| 재질 | `SurfaceKind`+roughness/metalness | `Finish`+contrast/sss Color |
| paintSurface | quality/occlusion/detailSeed | detail/seed/rim/ao |
| 완성 캐릭터 | humanoid_renderer만 | **모든 PC/Mob** |

architecture는 공존을 경고하지만, **SKILL 워크플로우 4단계가 “render/ 또는 core/shading”으로만 얼버무리고** 어느 쪽이 어느 산출물인지 매핑하지 않는다. AI가 `Finish.metal`을 A API에 넣거나 `keyDir` 부호를 B에 쓰면 즉시 실패.

### 3.5 아이소 특수성: 문서 A는 강하고, 작품 B는 아이소가 아님

- 아이소 규칙(접지 타원, squash 1회, top plane, 8방향 near/far)은 `isometric.md`+`humanoid_renderer`+`main.dart`에 **일관**.
- 완성 PC/Mob의 `groundShadow(..., 250, 42)` 등은 **초상용 납작 타원**이지 2:1 아이소 접지 규약이 아님.
- 스킬이 “모든 캐릭터를 아이소에 맞게”라고 하면서 워크플로우가 아이소 렌더러를 가리키면, AI는 트랙 B 품질을 아이소에 이식할 때 **좌표계(`kStage` vs 발원점 0)와 페이싱 부재**에 막힌다. 이식 가이드가 없다.

### 3.6 절차 생성 품질 장치

잘 된 부분: 원형 다이얼 비겹침(`spec.dart:116-148`), `branch(11)`, `bell`, Palette band, squint/시드24 검증 서술이 실행 가능에 가깝다.

약한 부분:
- 몬스터는 “확장 패턴” 문서만 있고 **구현된 MonsterSpec 없음**. 실제 4 Mob은 완전 수작업.
- `shapeBias` 미구현 → 원형→도형 언어 파이프라인이 코드에 없음.
- 성별·얼굴형·헤어 스타일 축이 Spec에 빈약(`hairLength` 정도) → PC 개성(lyra 브레이드, seraphine 스커트 등)을 절차로 못 냄.

### 3.7 메타·실행 가능성 결함

- 스킬 이름 `abc` / 명령 `def` → 리네임 미완료. 트리거·슬래시 커맨드 실패 위험.
- 문서 전용 API: `Facing.lerp`, `MonsterRole`, `shapeBias`, 별도 `actor_component.dart`.
- `paintSurface` 시그니처를 A로만 가르치면 B 파일에서 컴파일 실패.
- “수정보완해 주세요” 요청이어도 본 분석은 읽기 전용 — 권고만 §5.

## 4. 리스크 · 함정

- **가장 큰 함정**: AI가 스킬만 보고 `HumanoidSpec` 변종을 양산 → 로스터 품질 붕괴, anatomy 철학 위반.
- **조명 규약 혼동**: 계보 A/B `dir` 부호 반대 → 전신 명암 반전 (SKILL 실수 표에 있지만 **어느 LightRig인지** 명시 부족).
- **“접촉 그림자 필수” 문서 vs 절차 코드 미구현** → 체크리스트를 통과했다고 보고해도 시각은 스티커.
- **초상 캐릭터를 인게임에 붙일 때**: 8방향·Pose·squash·공유 LightRig 부재 → 전면 재작성 비용.
- **가상 API 복사** (`Facing.lerp` 등) → 컴파일 실패로 루프.
- **아틀라스/임포스터** 권고는 성능 문서에 있으나 게임 루프 미연결 — 조기 최적화 함정.
- **이름 리네임 잔여물** (`abc`/`vis`) → 스킬 미로딩 시 분석 전체가 무의미.

## 6. 불확실 · 미확인

- 절차 `HumanoidRenderer`의 **실기 시각 품질**(실제 스크린샷/플레이 체감)은 코드 리딩만으로 AAA 여부를 단정할 수 없음. 구조상 디테일 상한은 트랙 B보다 낮아 보임 `[판단]`.

- Flame 실전 맵 씬(타일맵·다중 액터 전투)은 `main` 뷰어 수준; performance 예산표의 실측 여부는 미확인.
- 팀 의도: 트랙 A를 **미래 본선**, 트랙 B를 **쇼케이스**로 두는지, 반대로 B를 본선으로 둘지 — cowork-prompt는 스킬 감사를 요청할 뿐 최종 제품 방향을 고정하지 않음 → **사람 결정 필요**.
- `lib/` 약 13400줄 중 anim/library·stage 전 클립 품질, 웹 Impeller 실측은 범위 밖.
- Pass 2 적대 리뷰 시 특히 “트랙 B를 문서에 넣으면 분량 폭발 vs 필수 최소 세트” 경계를 다시 자를 것.
